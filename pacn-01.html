PACN-01 // FOVEA ENGINE // PEREGRINE MISSION CONSOLE

From airborne relay concept to distributed mission node.

PACN-01 has evolved into a modular airborne edge-node architecture intended to combine communications, sensing interfaces, cooperative tracking, mission compute, and operator decision support. FOVEA is the software layer being built to make those pieces operate as one mission system.

ACTIVE ENGINEERING DEVELOPMENT

SYSTEM EVOLUTION

The architecture changed as the mission problem became clearer.

The original PACN-01 concept centered on restoring or extending RF connectivity from an airborne node. Current development keeps that function, but treats communications as one service inside a broader mission architecture rather than the entire product.

ORIGINAL CONCEPT

Airborne RF relay.

Extend line-of-sight, bridge terrain, restore temporary communications, and place a useful RF node above infrastructure-limited areas.

CURRENT ARCHITECTURE

Airborne edge mission node.

Configurable RF interfaces, sensing/radar integration points, network topology, cooperative track exchange, local mission compute, and FOVEA services.

NEXT INTEGRATION STEP

Representative hardware + surrogate airframe.

Move software and interfaces onto representative compute, radios, sensors, and a mature flight platform before committing to a purpose-built airframe.

PUBLIC ARCHITECTURE VIEW

Sense. Communicate. Fuse. Decide. Exchange.

The public architecture intentionally stays at the functional level. Mission-specific RF, sensor, waveform, and implementation details are configuration-dependent and are not represented here as fixed specifications.

FOVEA ENGINE + PEREGRINE MISSION CONSOLE

Software is already beyond a slide-deck concept.

The current FOVEA software baseline is an engineering MVP. It packages native mission/simulation logic with a ground-station backend and the Peregrine Mission Console operator interface for Windows and Linux engineering use.

HARDWARE TRANSITION

The fastest path to a credible flight demo is not to invent every subsystem at once.

HARDWARE POSTURE

Integrate on a mature platform first. Purpose-build later.

Peregrine is looking for a prototyping / airframe partner that can support a representative airborne integration path. The immediate objective is to retire software, RF, payload, power, thermal, and flight-interface risk without making the first flight article carry the burden of validating an entirely new air vehicle.

AIRFRAME / UAS PARTNER

Mature surrogate platform.

Payload volume and mass, power, mounting, flight integration, operating approvals, flight-test support, and a path to repeated engineering sorties.

RF / SENSOR PARTNER

Representative mission hardware.

Radios, antennas, sensors, radar interfaces, embedded compute, time/position sources, and instrumentation suitable for integration and test.

GOVERNMENT / PRIME PARTNER

Real problem and evaluation context.

Representative mission threads, system constraints, interfaces, success criteria, test venues, and scoped engineering work that creates useful evidence.

RESEARCH / TEST PARTNER

Independent technical depth.

RF propagation, radar, autonomy, controls, aero/structures, HIL/SIL, modeling, instrumentation, and independent validation support.

P-360 RELATIONSHIP

P-360 is the later purpose-built aircraft path, not a prerequisite for early PACN-01 validation.

P-360 Stoop is a design-stage Group 3 VTOL aircraft concept intended to support persistent sensing and communications payloads in later development phases. Peregrine's near-term integration strategy is to use a mature surrogate airframe where practical, learn from flight-relevant integration, and feed those constraints back into P-360 rather than waiting for a bespoke aircraft before validating the mission system.

Design-status note: P-360 performance values are engineering objectives until validated by prototype hardware and flight test.
